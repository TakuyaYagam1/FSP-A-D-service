# Пропуск поставки

## Задача
После согласования маршрута владелец дела вручную выпускает итоговый пропуск. Владелец, назначенный перевозчик и назначенный инспектор могут открыть его из существующего дела или ссылки на поставку и скачать PNG, в том числе после истечения временных подтверждений. В интерфейсе это шаг «4. Пропуск».

## Подходы
- Только показывать текущий статус на прежнем PNG-черновике: быстро, но документ не связан с поставкой и исчезает из сценария после истечения подтверждений. Не подходит.
- Выпускать пропуск автоматически при втором подтверждении: удобно участникам, но убирает явное завершающее действие владельца. Не выбран.
- Ручной выпуск с записью о выпуске для конкретной поставки: выбран пользователем. У действия есть однозначный момент и результат, доступный трем связанным аккаунтам.

## Поведение
1. Шаг 4 до готовности маршрута закрыт. Текущая готовность определяется действующим алгоритмом соответствующей версии backend; алгоритм подтверждений, срок действия и доступ к коду не меняются.
2. Когда маршрут готов, владелец нажимает «Выпустить пропуск». Сервер проверяет владельца и актуальную готовность, сохраняет одну запись о выпуске на поставку и возвращает ее. Повторный запрос идемпотентен.
3. После выпуска владельцу, перевозчику и инспектору доступно чтение записи. Чужому аккаунту запись не раскрывается. Выпуск остается доступен после истечения подтверждений; повторные подтверждения не создают новый выпуск.
4. UI строит скачиваемый PNG из полученных с сервера данных дела, поставки и выпуска. На нем указаны номер дела, маршрут, участники, время выпуска и «МАРШРУТ ГОТОВ». Кода поставки и утверждения о двух уникальных подписях на нем нет. PNG является игровым пропуском, не юридически значимой подписью.
5. Старый несогласованный PNG-черновик остается доступен владельцу как отдельное действие рядом с согласованием; существующие preview API и renderer не переиспользуются для выпуска, поскольку они принимают произвольный EPS и привязаны только к владельцу.
6. Назначенные участники открывают шаг 4 через уже выданную ссылку на поставку. Новая система ролей и глобальный список назначений для участников не вводятся.

## Данные и API
Аддитивная миграция добавляет таблицу `route_passes` с первичным ключом `route_slot_id`, временем `issued_at` и внешним ключом на `route_slots`. Чтение собирает неизменяемые поля дела и назначений по связанным таблицам. Новый `GET /api/v1/route-slots/{slot_id}/pass` отдает доступному аккаунту текущую готовность и состояние выпуска; новый `POST` по тому же пути выполняет только выпуск владельцем. В ответах нет `slot_code`. Готовность после выпуска может истечь, но запись о выпуске остается. Клиент использует серверное состояние, не `sessionStorage`, как источник истины.

## Проверки и ограничения
Тесты на владельца, обоих участников, чужой аккаунт, попытку выпуска до готовности, повторный выпуск, исчезновение Redis-состояния после выпуска и отличие уязвимой/исправленной схем подтверждений. Оба frontend и backend собираются, генерация ogen/sqlc/Wire не дрейфует, checker остается зеленым. Основная рабочая БД обновляется без удаления томов и существующих дел; patch backend не запускается против нее, чтобы не запускать его миграции на чужих данных. Отдельной отправки документа и хранения PNG-файла на сервере нет: хранится факт выпуска, а изображение воспроизводится из него при скачивании.
